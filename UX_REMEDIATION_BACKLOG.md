# Бэклог по UX-аудиту — в порядке критичности

Источник: [`ADMIN_UX_AUDIT.md`](ADMIN_UX_AUDIT.md), 12.09.2026.

## P0 — деньги, данные и необратимые ошибки

Делать до любых визуальных улучшений. Эти задачи снижают риск неверного долга,
потери журнала или ложного статуса велосипеда.

| № | Задача | Готово, когда | Зависимости |
|---:|---|---|---|
| P0.1 | Запретить будущую дату завершения аренды | DateInput не даёт выбрать дату после сегодня; серверная `finish_tenant_rental` также отклоняет её; есть тесты часового пояса Europe/Warsaw. | Нет |
| P0.2 | Сделать финансовый старт действительно безопасным | Меню называется «Новый финансовый старт», перед сохранением нужно ввести подтверждение; сервер сохраняет неизменяемый audit snapshot удаляемых записей. | P0.4 |
| P0.3 | Добавить отмену ошибочного завершения аренды | Оператор может отменить завершение только если велосипед не занят; возвращаются assignment/status/платёжный график; операция журналируется. | P0.4, P0.5 |
| P0.4 | Ввести неизменяемый аудит финансовых и арендных действий | Для платежа, начисления, корректировки, смены велосипеда/тарифа, reset и завершения хранятся actor, время, before/after, причина. | Нет |
| P0.5 | Привязать итоговое начисление к событию `rental_ended` внешним ключом | Коррекция завершения всегда находит ровно свой charge, а не сопоставляет по комментарию и дате; старые записи мигрированы. | P0.4 |
| P0.6 | Проверить серверные инварианты велосипеда | Нельзя одновременно: иметь bike у двух клиентов, считать его свободным при активной аренде, удалить/отправить в maintenance занятый bike без понятного перехода. Добавить транзакционные тесты. | Нет |
| P0.7 | Защитить от двойной отправки финансовых форм | Все submit-кнопки блокируются до ответа; RPC идемпотентны или принимают idempotency key; e2e покрывает double-click и retry. | Нет |
| P0.8 | Разделить «Архивировать клиента» и «Закрыть аренду» в бизнес-правилах | Архив не может молча создавать/искажать финальный расчёт; UI и backend явно выбирают нужный путь. | P0.3 |

## P1 — ежедневная скорость работы администратора

Делать следующим релизом. Эти задачи не должны менять историю денег, но заметно
сократят число ошибок и время обслуживания.

| № | Задача | Готово, когда | Зависимости |
|---:|---|---|---|
| P1.1 | Создать единый блок «Статус аренды» в карточке клиента | Видны статус, велосипед, старт, ближайший платёж, долг и две разные операции: «Завершить аренду» / «Архивировать клиента». | P0.8 |
| P1.2 | Добавить поиск и быстрые фильтры | Поиск по имени, телефону, slug и велосипеду; фильтры «есть долг», «просрочен», «без велосипеда», «архив». Состояние сохраняется в URL. | Нет |
| P1.3 | Добавить расшифровку баланса | По клику «Как рассчитано?» видны дата среза, суммы начислений, оплат, корректировок и остаток по каждому charge. | P0.4 |
| P1.4 | Явно объяснить последствия смены велосипеда/ставки | До сохранения показывается preview: какой event будет создан, какие будущие начисления изменятся, какая дата эффективности. | P0.6 |
| P1.5 | Ввести явные эффективные даты изменений | При изменении велосипеда, батареи, ставки и дня платежа оператор выбирает «сегодня» или другую дату; нельзя незаметно переписать прошлое. | P0.4 |
| P1.6 | Доработать завершение аренды как settlement | Отдельные поля: финальное начисление, удержание депозита, штраф/повреждение, возврат/аванс; внизу итог баланса. | P0.5 |
| P1.7 | Добавить массовые действия по начислениям | На экране «Платежи сегодня» можно утвердить все выбранные начисления с итоговой суммой и confirmation. | P0.7 |
| P1.8 | Сделать историю аренды читаемой timeline | Смена bike, батареи, тарифа, пауза, окончание и финансовые действия читаются как единая хронология с автором. | P0.4 |
| P1.9 | Добавить понятную обработку конфликтов параллельного редактирования | При сохранении устаревшей карточки пользователь видит, что изменилось, и выбирает обновить/перезаписать. | P0.4 |
| P1.10 | Единый статус данных и кнопка повторной загрузки | В каждом error-state есть Retry; глобально видны «нет сети», «обновлено N мин назад», «синхронизируем». | Нет |

## P2 — надёжная работа при плохом интернете

Зависит от завершённого local-first кэша. Цель — не только быстро открыть
данные, но и никогда не создавать иллюзию сохранения без сети.

| № | Задача | Готово, когда | Зависимости |
|---:|---|---|---|
| P2.1 | Проверить изоляцию локального кэша по пользователю | После logout/login другого администратора старый snapshot недоступен; есть e2e-тест. | Нет |
| P2.2 | Добавить offline-индикатор и дату свежести | Пользователь всегда видит offline/online и время последней успешной синхронизации. | P1.10 |
| P2.3 | Создать очередь исходящих изменений | Платёж/правка, созданные offline, помечены «ожидает отправки», безопасно повторяются после сети и могут быть отменены. | P0.7, P1.9 |
| P2.4 | Разрешить offline только чтение до готовности очереди | Кнопки изменения блокируются с ясной причиной; данные открываются моментально из кэша. | P2.2 |
| P2.5 | Нагрузочно проверить старт на слабой сети | Lighthouse/Playwright: cold cache, warm cache, Slow 3G, offline reload; зафиксировать бюджеты. | P2.1 |

## P3 — понятность, качество интерфейса и отчётность

Можно выполнять независимо и небольшими итерациями.

| № | Задача | Готово, когда | Зависимости |
|---:|---|---|---|
| P3.1 | Унифицировать язык интерфейса | `Statement` → «Выписка», `rental ended` → «Аренда завершена», один словарь статусов во всех экранах. | Нет |
| P3.2 | Добавить легенду графика и недопустить пустой график | Текущая неделя/прогноз объяснены; хотя бы одна серия всегда включена; есть accessible labels. | Нет |
| P3.3 | Поддержать `prefers-reduced-motion` | Анимация графика отключается для пользователей с reduced motion. | Нет |
| P3.4 | Сделать CSV-экспорт выписки | Экспорт учитывает фильтр периода, содержит начисления/оплаты/корректировки/баланс. | P1.3 |
| P3.5 | Добавить печатную финальную выписку аренды | В одном документе: клиент, велосипед, период, финальный долг, депозит, оплата, причина. | P1.6 |
| P3.6 | Добавить управление обслуживанием велосипеда | У maintenance есть причина, дата начала/ожидаемого окончания и задача. | P1.8 |
| P3.7 | Сделать связи задач с клиентом и велосипедом явными | Карточки tenant/bike показывают открытые/просроченные задачи и быстрый переход. | Нет |
| P3.8 | Доступность: клавиатура, focus, zoom | E2E: tab order, Escape, focus return; ручной visual test 200% zoom и 320px. | Нет |
| P3.9 | Добавить подтверждение потери несохранённых изменений | При закрытии формы профиля/модала с dirty state показывается предупреждение. | Нет |

## Порядок релизов

1. **Релиз A — безопасность денег:** P0.1, P0.4, P0.6, P0.7.
2. **Релиз B — безопасное завершение аренды:** P0.2, P0.3, P0.5, P0.8.
3. **Релиз C — быстрый операционный экран:** P1.1–P1.5, P1.10.
4. **Релиз D — финансы для оператора:** P1.6–P1.9, P3.4–P3.5.
5. **Релиз E — плохой интернет:** P2.1–P2.5.
6. **Релиз F — polish:** P3.1–P3.3, P3.6–P3.9.

## Не делать пока

- Новые большие графики и декоративные дашборды: сначала доверие к данным и
  быстрые ежедневные операции.
- Полный редизайн: он не решит риск потери истории и смешение статусов аренды.
- Offline-запись без idempotency и обработки конфликтов: это опаснее, чем
  честный read-only offline режим.
