# Аудит Rent — 20 сентября 2026

Аудит текущего рабочего дерева, включая уже существовавшие незакоммиченные изменения. Код приложения и миграции при аудите не менялись. SQL проверен статически; соответствие миграций удалённой базе и развёрнутых Edge Functions не проверялось. Записи в рабочую базу не выполнялись. Браузерные воспроизведения использовали локальный Vite и перехваченные ответы API с искусственными данными.

## Вывод

React/Vite + Supabase подходят этому приложению. Главный источник проблем — несовпадение контрактов данных и смысла действий между интерфейсом, финансовым расчётом и SQL. Особенно опасны операции, которые выглядят обычным редактированием, но закрывают другую аренду, удаляют историю или меняют деньги.

Хорошая основа уже есть: финансовые функции выделены, основные связанные изменения выполняются RPC-транзакциями, есть RLS с `admin_users`, lazy loading, unit-тесты и CI. Полная перепись не нужна. В первую очередь нужны исправления пользовательских сценариев, строгие контракты и проверки на настоящей тестовой БД.

## P1: исправить до дальнейшего расширения функций

### 1. Публичная выписка может показывать другой долг

- Источник: `supabase/migrations/20260906000002_harden_public_and_admin_rls.sql:88`; `src/utils/paymentLedger.ts:145`.
- Публичный RPC не возвращает `payment_adjustments.balance_override`, хотя административный запрос получает его и расчёт использует как установку нового баланса.
- Воспроизведение: стартовый долг 300 zł, корректировка «установить баланс 100 zł», `amount=0`. Полный объект даёт 100 zł; публичная проекция — 300 zł.
- Последствие: клиент и администратор видят разные обязательства; оплата и разбор спора становятся ненадёжными.
- Исправление: отдельная новая миграция публичной проекции, обязательный DTO финансового расчёта и контрактный тест одинакового результата admin/public для одинаковых операций. Проверять также нулевой и отрицательный контрольный баланс.

### 2. «Отмена» подтверждения заявки всё равно зачисляет деньги

- Источник: `src/pages/admin/AdminPaymentApprovals.tsx:44`.
- При подтверждении `window.prompt(...) || ''` превращает `null` от отмены в пустой комментарий, затем выполняется `approvePaymentRequest`.
- Браузерное воспроизведение: нажать «Подтвердить», закрыть prompt через Cancel → один вызов `approve_payment_request` и уведомление об успешном зачислении.
- Исправление: отдельный диалог с суммой, клиентом, способом и фактической датой оплаты. Cancel всегда завершает сценарий без мутации. После успеха обновлять также карточку клиента и dashboard: сейчас обновляются только заявки и утверждения.
- SQL заявки использует `CURRENT_DATE`, а не дату получения денег: при поздней обработке история получает дату подтверждения. Это следует явно согласовать с финансовым смыслом операции.

### 3. Создание аренды предлагает велосипеды без названий и с неверной тарифной подсказкой

- Источники: `src/pages/admin/AdminDashboard.tsx:52`, `:404`; `supabase/migrations/20260828000005_trim_dashboard_snapshot.sql:30`; `src/utils/rentalPricing.ts:56`.
- Dashboard RPC возвращает велосипеды `{id, status}`. Тот же массив передаётся форме, которой нужны `model`, `type`, текущий арендатор.
- Браузер с реальным форматом ответа: пункт выбора содержит только «СВОБОДЕН»; после выбора кнопка продолжает показывать «Нет велосипеда», хотя ID выбран.
- При неизвестном `type` тарифный помощник считает велосипед MTB. Например, для 13 Ah предложит 143 zł вместо FAT-тарифа 158 zł.
- Исправление: загружать полноценный список доступных велосипедов при открытии формы; отдельный обязательный тип `RentalBikeOption`. Не использовать DTO статистики как DTO формы.

### 4. Завершение аренды по умолчанию обнуляет последнее начисление

- Источники: `src/pages/admin/TenantRentalModals.tsx:68`; `supabase/migrations/20260827000003_pay_after_rental_week.sql:419`.
- Новое завершение получает `finalAmount=0`. SQL находит начисление за период, содержащий дату завершения, заменяет сумму введённой и при нуле переводит его в `waived`. Текст формы говорит о добавлении итогового начисления, хотя может произойти замена существующего.
- Это не утверждение о списании всего долга: меняется последнее соответствующее начисление. Но простое подтверждение формы может бесплатно закрыть неполную неделю.
- Дата завершения не имеет `max`; SQL также не запрещает будущую дату, ссылаясь в комментарии на защиту браузера. Браузером подтверждено отсутствие `max`. Будущее завершение немедленно освобождает велосипед.
- Исправление: предварительный расчёт периода и баланса «до → после», явное объяснение замены, обязательная причина нулевого начисления, запрет будущего немедленного закрытия. Плановое завершение должно быть отдельным действием. Возврат депозита и остаток долга включить в итоговый расчёт.

### 5. «Редактировать баланс» удаляет финансовую историю

- Источники: `src/pages/admin/TenantBalanceSection.tsx:43`; `src/pages/admin/TenantRentalModals.tsx:45`; `supabase/migrations/20260727000001_029_accounting_reset.sql:40`.
- За нейтральным названием в меню «+» находится удаление платежей, корректировок, начислений и истории тарифов. Предупреждение внутри формы есть, но действие остаётся рядом с обычным вводом платежа.
- Уже существует безопаснее устроенная альтернатива: «Корректировка → Установить баланс на дату», сохраняющая историю.
- Исправление: обычное редактирование направить в контрольную корректировку. Сброс учёта вынести в отдельный административный инструмент с экспортом/снимком, явным названием и аудитом операции. Не использовать его для исправления ежедневных ошибок.

### 6. Выбор занятого велосипеда закрывает аренду другого клиента

- Источники: `src/pages/admin/TenantBikeSelector.tsx:69`; `supabase/migrations/20260828000002_fix_bike_reassignment_order.sql:46`; создание — `20260827000003_pay_after_rental_week.sql:346`.
- Выбор занятого велосипеда доступен. RPC сам вызывает `close_tenant_rental` для предыдущего клиента и отвязывает его. Отдельного подтверждения последствий в формах нет.
- Исправление: по умолчанию только свободные велосипеды. Передача занятого — отдельный сценарий с двумя клиентами, датой, финансовым итогом прежней аренды и подтверждением. Изменение уже занятого статуса должно валидироваться сервером в транзакции.

### 7. Приватный offline-кэш возвращается после выхода

- Источники: `src/components/Layout.tsx:80`; `src/shared/lib/offlineQueryCache.ts:90`; `src/main.tsx:30`.
- Logout очищает IndexedDB/localStorage, но не `QueryClient`. Подписка продолжает сохранять успешные запросы, нет изоляции по пользователю. Изменение auth-сессии само по себе также не чистит кэш.
- Воспроизведение браузером: открыть dashboard с тестовым клиентом → выйти → через 1,2 секунды `rent-offline-cache-bootstrap-v1` снова содержит его имя.
- Это подтверждённое сохранение данных после logout, а не доказательство удалённой утечки. На общем устройстве/при смене аккаунта это нарушает ожидаемую границу доступа.
- Исправление: сначала остановить persistence и отменить запросы, очистить память и оба хранилища; учитывать auth events. Кэш привязать к user/project/schema, восстанавливать только после проверки сессии. TTL считать по возрасту данных: нынешний `savedAt` обновляется при повторной записи старого состояния.

### 8. Google Tasks push проверяет вход, но не права администратора

- Источник: `supabase/functions/google-tasks-push/index.ts:24`, `:39`, `:47`.
- После `getUser()` функция принимает `taskId` и читает/изменяет задачу через service-role client. Проверки `is_admin`/`admin_users` нет.
- При развёртывании этой версии любой валидно вошедший неадминистратор, знающий ID, сможет инициировать операцию синхронизации; для помеченной удалённой задачи предусмотрено окончательное удаление. Наличие таких аккаунтов и развёртывание этой версии не проверялись.
- Исправление: до привилегированного обращения проверить admin membership и доступ к задаче пользовательским клиентом. Добавить отрицательный интеграционный тест для Auth user вне allowlist.
- Service role обходит RLS, поэтому политики таблицы сами по себе этот endpoint не защищают: [документация Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

### 9. Одна физическая батарея может оказаться у нескольких клиентов

- Источники: `src/pages/admin/AdminTenantDetail.tsx` — редактор батарей; `src/utils/rentalPricing.ts:17`; `supabase/migrations/20260828000017_batteries_inventory.sql`.
- Назначение записывается в JSON внутри текстового `battery_config`. В миграциях нет FK/уникальности назначения и синхронизации статуса батареи с арендой. Два селектора не исключают батарею, выбранную в другом слоте.
- В итоге код батареи в карточке не гарантирует реальное местонахождение; проверка `status === available` не обеспечивает эксклюзивность выдачи.
- Исправление: таблица назначений с FK, активным уникальным назначением батареи и историей выдачи/возврата. Выдавать/освобождать вместе с арендой в одной транзакции.

### 10. Ошибка Google Tasks выглядит как несохранённая задача, хотя она уже создана

- Источники: `src/features/tasks/api.ts:52`; `src/features/tasks/queries.ts:18`.
- Сначала выполняется INSERT в Supabase, потом в production вызывается Google Tasks. При ошибке или warning вызывается `throw`; UI показывает «Ошибка сохранения», успешная инвалидация не выполняется.
- Повторное нажатие для новой задачи может создать ещё одну запись. Локальный dev/e2e этот путь не проверяет из-за `import.meta.env.PROD`.
- Исправление: сохранение задачи завершает основную операцию; синхронизация имеет отдельный статус и повтор по тому же ID. Для надёжной доставки — очередь/outbox, уникальный ключ операции и независимый retry.

## P2: ошибки и ограничения, заметно ухудшающие ежедневную работу

### 11. Отмена редактирования оставляет черновик

`src/pages/admin/AdminTenantDetail.tsx:75`: форма инициализируется только при `!editForm`; кнопка отмены лишь закрывает редактирование. Браузер: изменить имя на `UNSAVED`, отменить и снова открыть — остаётся `UNSAVED`. Позднее сохранение другого поля может заодно записать отменённое имя. Создавать черновик заново при входе в режим редактирования, сбрасывать на Cancel и после успешного сохранения. Не переносить черновик между tenant ID.

### 12. Изменение дня оплаты меняет дату начала аренды

`src/pages/admin/TenantCreateModal.tsx:35`: выбор weekday пересчитывает `next_payment_date`, но это же поле показано как «Дата начала аренды» и передаётся RPC как начало. Оператор не может независимо указать фактическую выдачу и желаемый платёжный день. Разделить `started_on`, `first_due_on`, `payment_weekday`; показать цену и длину первого периода.

### 13. Контрольный баланс одного дня имеет неочевидный порядок

`src/utils/paymentLedger.ts:162`: сортировка только по дате и типу ставит все корректировки перед всеми оплатами, игнорируя время создания. Пример: утром оплата 50, вечером установили актуальный долг 100 → функция даёт 50. Если контрольная точка означает начало дня, это математически объяснимо, но UI этого не говорит и обещает считать от введённой суммы следующие операции. Нужно определить бизнес-смысл — начало дня, конец дня или момент — и одинаково реализовать порядок в БД, UI и тестах. Для нескольких корректировок одного дня нужен детерминированный дополнительный ключ.

### 14. Частичная поздняя оплата обозначается «вовремя»

`src/pages/admin/PaymentHistory.tsx:172`: Weeks берёт первую оплату с allocation к начислению. При начислении 100, оплате 50 в срок и оставшихся 50 через два дня выбирается первая дата и выводится «Оплачено вовремя». Проверено на результате `buildPaymentLedger`. Нужна дата полного закрытия обязательства, а не первой частичной оплаты. Отдельно показывать «частично оплачено», остаток и дату погашения.

### 15. Графики искажают смысл финансовых данных

- `src/components/TrendChart.tsx:26`: каждая серия размещается по собственным индексам, подписи берутся только из первой. При разных пропущенных месяцах одинаковая X-позиция означает разные даты. `dashboardSelectors.ts` дополнительно удаляет пустые/нулевые периоды. Нужна единая календарная ось с заполненными нулями.
- `src/pages/admin/PaymentHistory.tsx:149`: «график баланса» использует `entry.signedAmount`, то есть движение, а не остаток. Для объединённой строки начисление+оплата берётся только начисление: полностью оплаченная неделя выглядит красным долгом. Выбрать явный смысл: график движений или настоящий остаток после всей строки.
- Прогноз текущей недели в серии «Оплаты» нужно визуально и численно отделять от уже полученных денег.

### 16. Главная страница и журнал теряют место на телефоне

- Воспроизведено: viewport 320 px, document 411 px; за экран выходят переключатели «Мес/Год» dashboard.
- `PaymentHistory.tsx:118`: при `showChart` сетка всегда резервирует 25% ширины, хотя график скрыт до `lg`. На мобильном журнал необоснованно сжат.
- Исправление: перенос/компактная компоновка фильтров, двухколоночная сетка только на `lg`. Проверять длинные имена, крупные суммы, 320/393 px и открытые формы, а не только пустой dashboard.

### 17. Просроченные утверждения исчезают из рабочей очереди

`fetchTodayPaymentApprovals` в `src/features/tenants/api.ts:146` выбирает ровно сегодняшний день; компонент повторяет фильтр. Вчерашние неутверждённые начисления не видны в этой очереди, хотя остаются в индивидуальном журнале. На экране можно увидеть «Все сегодняшние платежи утверждены», имея старые непроверенные записи. Нужна общая очередь необработанных начислений `due_date <= today`, группы «просрочено/сегодня» и раздельные понятия «начисление утверждено» / «деньги получены».

### 18. Даты и данные могут устаревать в открытом приложении

`AdminDashboard.tsx:54` фиксирует дату при монтировании; `PaymentHistory` мемоизирует расчёт только по tenant. В `main.tsx` отключён refetch на focus. После полуночи/возврата в PWA расчёты могут оставаться вчерашними. Добавить общий business date в выбранной временной зоне, обновление при смене дня и возврате в приложение, видимую отметку последней синхронизации. В кредитных формах `toISOString().split('T')[0]` даёт UTC-день вместо локального возле полуночи.

### 19. Предсказуемые ссылки раскрывают финансовую историю

`src/utils/slug.ts` создаёт slug из имени с последовательным суффиксом. Публичный RPC доступен anon и по этому slug отдаёт имя, начисления, оплаты и события. Это намеренно публичный сценарий, но знание имени не должно автоматически давать доступ к персональной выписке. Рекомендация: отдельный случайный public token с перевыпуском/отзывом; slug оставить только удобным названием. Не отдавать `details` событий целиком: состав публичных полей задавать явно.

### 20. Модальные окна не удерживают фокус и не защищают черновик

`src/shared/ui/index.tsx:78`: есть Escape и backdrop, нет переноса/удержания/возврата фокуса, блокирования взаимодействия с фоном; backdrop закрывает заполненную форму. Добавить управление фокусом, подтверждение потери изменённых данных и блокировку повторной отправки. Для кредитных операций также отсутствует полноценный pending-state: повторное нажатие может создать несколько операций.

Поведение фокуса описано в [W3C Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). Это относится и к пользователям клавиатуры, и к предсказуемому возврату в рабочий сценарий после закрытия формы.

## Архитектурные изменения с наибольшей отдачей

1. **Контракты по назначению.** Развести `DashboardSummary`, `TenantAccounting`, `PublicTenantAccounting`, `RentalBikeOption`. Критичные поля не делать optional. JSON RPC валидировать на границе; убрать слепое приведение `as Tenant`. Тестировать DTO непосредственно против результата SQL на тестовой БД.
2. **Единый финансовый смысл.** Pure ledger оставить источником расчёта интерфейса; серверные команды отвечают за запись и инварианты. Зафиксировать правила знаков, расчётного дня, контрольных точек, неполной недели и депозита. Admin/public получают эквивалентные финансовые входные данные.
3. **Явная аренда и назначения оборудования.** Клиент — не аренда. Поступательно выделить rental episode со start/end/status, историей тарифа, bike/battery assignments. Не восстанавливать сложную удалённую beta-модель целиком без необходимости. Начать с реальных команд: выдать, заменить, вернуть, завершить.
4. **Аудит и повторяемость команд.** Финансовые исправления — сторно/корректирующая запись с причиной, автором, временем. Для создания платежа нужен request ID и уникальность на сервере: disabled кнопка не защищает от повтора после сетевого таймаута. Обновления снабдить version/updated_at для выявления конкурентной правки.
5. **Единые mutation hooks и кэш.** Сейчас ключи `['tenants']`, `['tenant', id]`, approvals и public history не образуют общего дерева; инвалидации легко пропустить. Для одной операции централизованно обновлять нужные projections. `fetchInventory` и `fetchBikes` не должны делить один key при разных наборах полей (`voice_code` есть только в одном).
6. **Чтение отделить от генерации начислений.** `fetchTenantDetail` и dashboard на чтении вызывают `ensure_*`; открытие экрана изменяет БД. Плановую генерацию делать явной серверной операцией/задачей, а чтение возвращает готовый snapshot. Сначала покрыть текущую генерацию тестами, чтобы не сломать расчёт.
7. **Dashboard — сводка, история — постранично.** Сейчас загружается вся история всех клиентов, затем строятся несколько графиков; все серии считаются до фильтрации выключенных. Отдельный запрос всех adjustments без пагинации уязвим к лимиту строк API (в локальном config — 1000). Нужны серверные агрегаты/периоды, фильтрация и пагинация. Это риск роста объёма, а не измеренная текущая деградация.
8. **Проверки БД и production-путей.** CI должен поднять изолированную Supabase, применить миграции и проверить anon/non-admin/admin, передачу велосипеда, повтор платежа, корректировки, публичную проекцию. Текущие моки не исполняют SQL. Production-specific Google push и service worker требуют отдельных сценариев.

## Как существенно улучшить ежедневный опыт

| Сценарий | Целевое поведение |
|---|---|
| Начало рабочего дня | Первым экраном очередь «требует действия»: долги, неподтверждённые поступления, возвраты, просроченные задачи. Графики ниже |
| Получил деньги | Видимая кнопка «Принять оплату» в строке и карточке; клиент, сумма, способ, дата, остаток после оплаты; один успешный результат |
| Выдача велосипеда | Клиент → свободный велосипед и батареи → фактический старт и тариф → понятная дата первой оплаты → итог → ссылка клиенту |
| Возврат | Последний период, начисление, депозит, доплаты/возврат, конечный остаток и статус оборудования до подтверждения |
| Вопрос «почему такой долг?» | Нажатие на баланс открывает начислено − оплачено ± корректировки, периоды, распределение частичных оплат и контрольные точки |
| Ошибочная операция | Доступное исправление с историей и причиной; отмена не выполняет финансовую команду |
| Работа на телефоне | Оплата и связь с клиентом доступны сразу; основные действия не спрятаны за универсальным «+»; фильтры сохраняются при возврате |
| Клиент открыл ссылку | «К оплате X до даты Y», понятная расшифровка, способ оплаты/контакт, сообщение об оплате и статус заявки |

Навигацию привести к предметным разделам: «Клиенты», «Парк», «Деньги», «Задачи». В «Деньгах» развести поступления арендаторов, проверку заявок и кредиты бизнеса. Сейчас пункт «Платежи» открывает кредиты, а клиентская публичная страница является только выпиской: кнопок отправки заявки и объяснения следующего действия в ней нет.

Полезные небольшие изменения: поиск по телефону/slug/коду велосипеда; фильтры в URL; «Скопировать ссылку клиенту» в мобильной карточке; единый русский язык вместо Statement/Weeks/In time/rental event; разные экраны «нет доступа», «нет интернета», «не найдено»; offline-индикатор и время актуальности баланса. Архивирование клиента с долгом не должно делать долг невидимым в общей очереди взыскания.

## Порядок выполнения

1. **Достоверность и безопасность действий:** пункты 1–8, восстановить проходящий E2E пути оплаты, проверить на изолированной БД. Критерий: одинаковый баланс admin/public; Cancel = ноль мутаций; завершение показывает последствия; после logout нет приватного кэша.
2. **Основные операции:** понятные выдача/замена/возврат, назначение батарей, явная оплата, сохранение/отмена черновика, корректировки без удаления истории. Критерий: оператор завершает каждую операцию без скрытых действий над другим клиентом.
3. **Доверие к истории:** частичные платежи, порядок контрольных точек, графики, очередь старых начислений, обновление даты. Критерий: любую сумму можно объяснить и воспроизвести тестом.
4. **Удобство и рост:** мобильная компоновка, фильтры, публичный кабинет, раздельная навигация, агрегаты, пагинация и синхронизация задач с очередью.
