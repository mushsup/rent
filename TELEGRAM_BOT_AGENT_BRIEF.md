# Telegram-бот Rent Krakow — инструкция для агента

## Цель

Создать Telegram-бота для клиентов сервиса аренды электровелосипедов Rent Krakow. Бот должен уменьшить ручную работу администратора: показывать клиенту его профиль и баланс, принимать заявки на пополнение баланса, напоминать о задолженности и открывать мобильный кабинет внутри Telegram.

Бот не должен сам подтверждать оплату. Любая заявка клиента сначала попадает администратору на проверку, после подтверждения создаётся фактическая запись оплаты в Supabase.

## Текущая архитектура сайта

- Frontend: React + TypeScript + Vite.
- Hosting frontend: Netlify.
- Backend/database: Supabase Postgres, Supabase Auth и RLS.
- Основной сайт: `https://rent-krakow.netlify.app`.
- Клиентская история: `/history/:slug`.
- Админка: `/admin`.
- Админская заявка на оплату: экран `AdminPaymentApprovals`.
- Таблица заявок: `public.payment_requests`.

В проекте уже есть RPC:

- `approve_payment_request(p_request_id, p_admin_note)` — атомарно создаёт оплату через `record_tenant_payment` и утверждает заявку.
- `reject_payment_request(p_request_id, p_admin_note)` — отклоняет заявку с обязательной причиной.

Схема заявки: `tenant_id`, `amount`, `payment_method` (`cash` или `bank_transfer`), `status`, `client_note`, `admin_note`, `appointment_at`, `requested_at`, `processed_at`.

## Рекомендуемый стек бота

- Node.js 20+.
- TypeScript.
- `grammy` для Telegram Bot API.
- Fastify или встроенный HTTP-сервер для webhook.
- `@supabase/supabase-js`.
- `zod` для проверки входных данных.
- Развёртывание отдельным сервисом: Render, Railway, Fly.io или VPS. Не помещать Telegram token во frontend или Netlify public environment.
- Для периодических напоминаний использовать cron-задачу на сервере или managed scheduler. Не полагаться на процесс, который может уснуть.

## Как связать Telegram с клиентом

Нужно добавить в Supabase отдельное поле `tenants.telegram_chat_id BIGINT UNIQUE` или отдельную таблицу `tenant_telegram_accounts`. Предпочтительно отдельная таблица, если позже понадобятся несколько аккаунтов и история привязок.

Первый запуск:

1. Клиент нажимает `/start` или deep link вида `/start link_<one_time_token>`.
2. Бот показывает короткое подтверждение личности: имя/телефон или одноразовый код из кабинета.
3. После подтверждения сохраняются `telegram_user_id`, `chat_id`, username и `tenant_id`.
4. Связывать только по username нельзя: username может измениться и может отсутствовать.
5. Повторный `/start` должен быть идемпотентным и не создавать нового клиента.

Если пользователь ещё не существует, бот может запустить короткое создание профиля: имя, телефон, согласие на обработку данных. Но арендатор, велосипед и договор не должны создаваться без отдельного завершения процесса и проверки администратором.

## Главное меню клиента

Использовать inline keyboard и Menu Button:

- `Мой профиль` — открыть Mini App на `/history/:slug` или защищённый клиентский маршрут.
- `Баланс` — кратко: долг/аванс/0, ближайшая дата, статус последнего платежа.
- `Пополнить баланс` — запрос суммы и способа оплаты.
- `Договор и аренда` — открыть пользовательский кабинет.
- `Помощь` — контакт администратора.

Mini App должен открываться кнопкой `web_app`, а не только обычной ссылкой. URL можно передавать с безопасным короткоживущим `startapp` параметром.

## Сценарий пополнения баланса

1. Клиент нажимает `Пополнить баланс`.
2. Бот показывает сумму долга и предлагает быстрые суммы: долг целиком, ближайший платёж, другая сумма.
3. Клиент выбирает `Банковская оплата` или `Наличные`.
4. Для наличных бот предлагает выбрать время визита или написать комментарий.
5. Бот создаёт `payment_requests` со статусом `pending`.
6. Клиент получает подтверждение: «Заявка отправлена. Баланс изменится после проверки администратором».
7. Администратор получает уведомление с inline-кнопками `Подтвердить` и `Отклонить`.
8. Подтверждение вызывает защищённый backend endpoint, который вызывает Supabase RPC. Бот не должен напрямую писать оплату из callback без серверной проверки.
9. После решения клиент получает сообщение. При отклонении причина обязательна.

До появления автоматического эквайринга не обещать клиенту мгновенное зачисление. Заявка — это не оплата.

## Напоминания о задолженности

Серверная cron-задача ежедневно выбирает клиентов:

- активный клиент;
- `balanceAtReference > 0` или есть просроченное начисление;
- нет уже отправленного напоминания за тот же день и тот же charge.

Рекомендуемый cadence:

- за 2 дня до платежа — мягкое напоминание;
- в день платежа — нейтральное напоминание;
- через 1 день — уведомление о просрочке;
- через 3–7 дней — более заметное уведомление и предложение связаться;
- после 7 дней — не спамить, передать администратору задачу.

Сообщения должны быть ясными, без манипуляций и скрытых штрафов. Показывать сумму, дату, количество дней просрочки и кнопку `Пополнить баланс`.

Пример:

> Баланс: задолженность 300 zł. Платёж просрочен на 3 дня. Нажмите «Пополнить баланс», чтобы отправить заявку. Оплата зачислится после проверки.

Хранить журнал отправок: tenant, charge, тип напоминания, дата, Telegram message id, результат. Повторная доставка webhook и повторный cron не должны создавать дубликаты.

## Безопасность

- Bot token только в secret environment variable.
- Supabase service role key только на backend бота.
- Никогда не отправлять service role key в Mini App.
- Все callback data короткие и подписанные/проверяемые на сервере.
- Для Mini App обязательно валидировать `Telegram.WebApp.initData` на backend. `initDataUnsafe` нельзя использовать для авторизации.
- Проверять `auth_date`, чтобы не принимать старые данные.
- Проверять, что Telegram user действительно привязан к конкретному tenant.
- Защищать admin actions отдельным списком Telegram admin IDs или Supabase admin auth.
- Использовать idempotency key для payment request и approve callback.
- Логировать ошибки без токенов, персональных данных и service role credentials.

## Mini App

Mini App — это существующий сайт, адаптированный под Telegram viewport:

- передавать Telegram theme variables;
- поддержать светлую и тёмную тему;
- учитывать safe area и Telegram back button;
- на старте отправлять `initData` на backend для валидации;
- после валидации backend выдаёт короткую сессию или разрешённый tenant slug;
- не доверять slug из URL без проверки связи с Telegram user.

Минимальные экраны:

1. Главная: баланс, статус недели, ближайший платёж.
2. История: начисления, оплаты, просрочки, аванс.
3. Пополнение: сумма, способ, комментарий, статус заявки.
4. Договор/аренда: текущий велосипед, даты и статус договора.

## Обработка ошибок и крайние случаи

- пользователь уже привязан к другому клиенту — остановить привязку и сообщить администратору;
- Telegram username изменился — использовать chat/user ID;
- пользователь заблокировал бота — пометить подписку неактивной, не удалять связь;
- повторное нажатие `Подтвердить` — безопасно вернуть уже обработанный результат;
- две заявки на одну сумму — не объединять автоматически, показывать историю заявок;
- заявка pending не должна менять баланс;
- удалённый/архивный клиент не получает новые напоминания;
- будущий платёж не считать задолженностью;
- часовой пояс проекта: Europe/Warsaw;
- деньги хранить как decimal/numeric, не использовать JS float для финансовых расчётов.

## План реализации

1. Создать отдельный bot service и `.env.example`.
2. Добавить migration для Telegram account/link table.
3. Реализовать `/start`, привязку и `/help`.
4. Реализовать главное меню и профиль Mini App.
5. Реализовать создание `payment_requests`.
6. Реализовать admin notification и approve/reject через backend.
7. Реализовать cron-напоминания с журналом идемпотентности.
8. Добавить тесты: auth validation, duplicate webhook, duplicate approval, blocked user, overdue reminders, timezone Europe/Warsaw.
9. Подключить webhook Telegram только после локального long polling теста.
10. Перед production сделать staging bot и прогнать сценарии на `DEMO · Платежи`.

## Критерии готовности

- клиент может безопасно открыть свой профиль из Telegram;
- бот не показывает профиль другого клиента;
- заявка наличными приходит администратору и не меняет баланс до approve;
- approve создаёт ровно одну оплату;
- reject требует причину;
- повторный callback не создаёт дубль;
- напоминание не дублируется чаще заданного cadence;
- все действия видны в логах;
- token и service role key отсутствуют в frontend bundle и git.
